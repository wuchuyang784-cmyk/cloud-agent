# Agent 本体运行环境与请求路由技术基线

> 状态：技术基线已确认（落地指导）
> 适用范围：控制台（管理面）+ 用户部署的 Agent 本体（数据面 / 对话面）
> 关联文档：`14-multi-tenant-agent-runtime.md`（多租户运行时，后端边界依据）、`USER-EXPERIENCE-BLUEPRINT.md`（UX 基线）、`apps/console-mvp`（本基线前端落点）
> 文档定位：本文确定 **Agent 本体的工作环境（运行时边界）、对话请求的路由方式，以及对应的技术落地方案**，作为前端与平台后端实现的统一依据。

## 一、产品形态确认

平台的核心交付物是：**用户通过控制台创建并部署 Agent 后，即可在云端直接使用该 Agent 与其对话；对话发生在 Agent 本体自带的前端 UI 中，而非控制台内。**

已确认的关键事实：

- **Agent 本体已存在**：前端 UI、Agent 循环、模型运行时、记忆、工具执行均由既有 Agent 本体提供，平台不重写对话能力。
- **每用户独立实例**：用户每创建并部署一个 Agent，平台基于同一 Agent 本体为其拉起一个**隔离的独立实例**，仅复用平台云端服务。
- **用户自配置**：API Key、模型、渠道、角色卡等由用户自行配置，落在该独立实例，不污染其他实例。
- **控制台定位 = 管理面 + 启动器 + 流量入口**：负责创建 / 部署 / 启动 / 监控 / 配置，不承载对话本身。

## 二、对话路由模型（核心）

对话数据路径：

```text
用户浏览器
  -> agent-{id}.bairui.app        （用户部署的 Agent 本体前端 UI，平台分配独立子域，已定）
  -> Agent 本体运行时             （该用户实例专属，配置已注入）
  -> 模型 API / 工具 / 记忆        （用户自配或平台默认）
```

控制台不参与对话转发，只做两件事：

1. **启动**：用户触发后，平台后端基于本体模板实例化、注入配置、**生成并返回该实例专属的独立域名 `agent-{id}.bairui.app`**。
2. **进入对话**：用户点"对话"→ 跳转到该实例的稳定独立域名 `agent-{id}.bairui.app` 打开 Agent 本体 UI 使用；用户也可**直接访问该独立域名**。控制台只是启动与管理入口，对话始终在独立域名下的 Agent 本体 UI 中进行。

### 2.1 独立域名即使用入口（核心确认）

每创建一个 Agent 并启动，**平台都会为其分配一个独立子域 `agent-{id}.bairui.app`**，启动完成后该域名即可访问——用户既可以在控制台内点"对话"进入，也可以把该域名当作书签/分享链接，**直接在浏览器打开就使用这个 Agent**。

- 独立域名是 Agent 的**稳定对外地址**：创建后绑定到该 `agent_id`，**永不改变**——无论启停、休眠、容器重建、还是规模化重路由，域名始终不变（停机时域名仍可达，返回"已停止，点击启动"类提示或自动触发冷启动）。
- 这与"每用户独立实例"模型一致：一个域名 = 一个用户的一个 Agent 实例，配置、会话、资源天然按域隔离。
- 鉴权：独立域名访问同样走平台 ticket / 登录态（见 3.1），未授权访问被拒，不暴露其他用户实例。

对话界面始终是 Agent 本体自带的前端 UI，平台只负责"拉起实例 + 分配域名 + 呈现"，不重写聊天能力。这一形态对应 `14-multi-tenant-agent-runtime.md` 的多租户边界：浏览器只寻址当前用户拥有的 Agent，本体机器凭证不进入浏览器响应。

## 三、平台侧需要的云服务能力

用户每个 Agent 独立运行在云端，意味着平台必须提供一套**部署 / 托管 / 多实例编排层**。它不是"再造一个 Agent"，而是"让已有本体按用户独立跑起来"的运行时与路由层。

| 能力 | 是否必须自有 | 说明 |
|---|---|---|
| 实例化 / 编排服务 | 必须（平台核心） | 创建后基于本体模板拉独立实例，分配 `embedUrl`，隔离配置 / 数据 / 运行时 |
| Agent 前端托管 | 必须（地址自有） | 本体前端部署在平台域名下，按实例出**独立子域**（已定：`agent-{id}.bairui.app`） |
| 用户配置注入（API Key / 模型 / 渠道） | 必须（平台侧） | 配置落到该实例，密钥隔离，不跨实例泄露 |
| 多租户隔离 | 必须（平台侧） | 每个 Agent 实例的配置、会话、运行时互相隔离 |
| 模型推理 | 可接第三方 | 用用户自配 Key 直连 DeepSeek / Claude / 通义等 |
| 底层算力 / IaaS | 可托管 | 容器服务 / CloudBase / 云厂商，不必自建机房 |

### 接入平台前，Agent 本体需补齐的改造

要让"每用户独立实例"成立，本体应满足其一：

- **无状态 + 配置外置**：配置不在代码中写死，启动时从环境变量 / 配置中心读取（最理想，克隆成本极低）。
- **支持多租户参数**：单一部署能按 `agent_id` 区分不同用户的配置与数据。

若本体现将配置编死在代码中，需先外部化，否则无法实现"每用户独立"。

### 部署路线（已定：每 Agent 启动 = 拉起独立容器 + 返回稳定域名）

> **核心决策（已确认）**：每个 Agent 启动，平台都**基于本体镜像拉起一个独立的容器实例**，并为其分配**专属独立子域 `agent-{id}.bairui.app`**。该域名在 Agent 创建后**永久绑定、永不改变**——容器重建、启停、规模化调度都不影响域名。

- **MVP / 当前形态**：本体打成容器镜像；用户创建 Agent 后，点击"启动"→ 后端拉起一个独立容器实例，分配独立子域 `agent-{id}.bairui.app`，返回 `embedUrl`。隔离性最好，实现最快。
- **规模化**：容器仍是每个 Agent 的确定承载形态（不做"共享池替代独立容器"的倒退）。平台采用 **Docker Swarm** 作为容器编排层——多节点集群统一调度、按 `agent_id` 起一个 service（副本数 1）即一个隔离容器实例；规模化只改**集群规模与调度策略**（加节点、Swarm 自动伸缩 service、预热镜像降冷启动、跨节点调度），而**子域形态与"1 Agent = 1 容器实例"模型保持不变**：对外地址永远是 `agent-{id}.bairui.app`，网关按 `agent_id` 解析到该 service 背后的容器。前端壳、ticket、独立域名不随规模化改造而变动。

### 3.1 域名与网关实现要点（已定：独立子域）

采用 `agent-{id}.bairui.app` 独立子域承载每个 Agent 本体的前端 UI，平台作为 DNS + 网关 + TLS 的持有方。

| 项目 | 方案 | 说明 |
|---|---|---|
| 子域格式 | `agent-{id}.bairui.app` | `{id}` 用平台分配的实例 ID，全局唯一 |
| DNS | `*.bairui.app` 通配 A / CNAME 记录 | 指向平台入口网关，无需逐实例建记录 |
| TLS | 通配符证书 `*.bairui.app` | 一次签发覆盖全部 Agent 子域；或用 ACME 按子域自动签发 |
| 网关路由 | APISIX / Kong 按 `Host: agent-{id}.bairui.app` 取 `{id}` → 查实例表 → 反代到该实例后端 | 实例表存 `agent_id ↔ 实际容器地址`；域名永久不变，容器重建 / 启停后实例表更新地址即可，用户无感；scale-to-zero 时网关触发冷启动再反代 |
| CSP `frame-ancestors` | 本体响应无需为控制台放行的跨域帧约束 | 对话不在控制台壳内嵌，用户直访独立子域，无跨域内嵌场景 |
| 鉴权 ticket | 不在 URL 注入 ticket（方案 A 已弃用） | 用户访问独立子域时由平台登录态 / 短期签名 ticket 在网关侧校验，登录态不跨域泄露（见 8.2 P7） |

**子域 vs 路径前缀的取舍（已决策依据）**：选子域因为① 每实例天然隔离，故障 / 限速 / 配额按域独立；② TLS 与 CSP 按域管理最干净；③ 控制台壳与子域不同源，跨域约束比路径前缀下同源套壳更清晰；④ 规模化后子域作为稳定对外契约不变，内部路由怎么换都行。

### 3.2 域名统一、运行实例隔离（归属关系）

采用独立子域后，常有一个误解："每个 agent 用自己的域名，是不是就跑在和平台不同的服务器上了？" 明确如下：

- **入口统一、实例隔离**：所有 `*.bairui.app`（含控制台 `console.bairui.app` 与每个 `agent-{id}.bairui.app`）的流量**统一经过平台入口网关**（APISIX / Kong）。网关是平台自有主权，按 `Host` 取出 `agent-{id}` → 查实例表 → 反代到该 agent 对应的运行时实例。因此"平台"作为**流量入口与路由中枢**是统一的。
- **平台服务 ≠ Agent 实例**：控制台前端/后端与某个 agent 的对话运行时**不是同一个进程**。每个 agent 子域背后是平台为它单独拉起、隔离的独立**容器实例**，配置、会话、资源互相隔离——这正是"每用户独立实例"的形态。域名创建后永久绑定该 `agent_id`，容器启停 / 重建都不改变域名，仅实例表里的容器地址随之更新。
- **算力可托管、不必同机**：这些 agent 实例由平台统一编排，跑在容器服务 / 云厂商上，可与控制台部署在不同节点 / 集群 / 可用区，不要求与平台控制台同机。
- **结论**：域名与路由归平台（统一网关），对话运行时归平台为每个 agent 单独托管但彼此隔离。即"平台是房东与物业，每个 agent 是租户各自独立的房间"——都是平台掌控，但运行实例层级分离。

> 因此"独立域名"≠"独立第三方服务器"。agent 仍运行在平台托管的**独立容器实例**内，只是对外暴露为一个**永久不变**的独立子域，便于隔离、证书管理与直接访问。

## 四、控制台前端改造（apps/console-mvp）

既有的 `ChatWorkspace` 内嵌 mock 聊天**不符合本形态**（那是"控制台内调试"假设）。本形态下控制台不内嵌"自己写的"对话，用户启动 Agent 后直接访问平台分配的稳定独立域名 `agent-{id}.bairui.app` 即可使用 Agent 本体自带 UI。

### 4.1 数据模型

```ts
interface Agent {
  // ...现有字段
  status: AgentStatus;     // 'running' 才代表云端实例已启动、可对话
  embedUrl?: string;       // 启动后的 Agent 本体独立域名（agent-{id}.bairui.app），控制台壳与用户直接访问共用同一地址
}
```

- `deploying` / `initializing` 的 Agent：`embedUrl` 为空，表示实例尚未就绪。
- `running` 的 Agent：`embedUrl` 由后端启动后返回，即该实例独立域名 `agent-{id}.bairui.app`，用户直接在浏览器打开该域名即可使用。

### 4.2 启动动作与标准使用流程

Agent 卡片 / 部署发布页提供"启动"入口。核心闭环极简：

**用户点击"启动" → 平台拉起该 Agent 独立实例 → 分配并返回专属独立域名 `https://agent-{id}.bairui.app` → 用户在浏览器访问该域名即直接使用该 Agent。**

- 调用后端启动 runtime → 分配并返回该实例独立域名 `embedUrl = https://agent-{id}.bairui.app` → `status` 变为 `running`。
- **域名即使用入口**：启动完成后，用户直接在浏览器打开该独立域名即可对话使用，控制台不是必经路径（也可在控制台点"对话"跳转/打开同一个域名，效果一致）。
- MVP 阶段先做**前端模拟启动**（点击启动后 `status` 变 `running` 并填入占位独立域名如 `https://agent-demo.bairui.app`），后端接口就绪后直接替换，前端结构不变。

> 已确认形态：用户启动 Agent 后直接访问平台分配的稳定独立域名即使用，控制台是管理面 + 启动器，不是对话承载方。

### 4.3 清理项

- 移除 `ChatWorkspace` 作为"对话"入口（内嵌 mock 与真实形态冲突）。
- `AgentCard` 的"对话"按钮由 `onOpenAgent`（内嵌 mock）改为打开该 Agent 的稳定独立域名 `agent-{id}.bairui.app`（新标签页 / 跳转，与用户直接访问同一地址）。
- 保留控制台"监控 / 配置"等管理面能力不变。

## 五、资源分配与回收（单实例 / 单用户维度）

每个 Agent 实例在云端运行时都会占用 CPU / 内存 / 网络，重负载还可能涉及 GPU。不治理就会出现"一个实例吃满节点、僵尸实例白占资源、计费不公平"。治理分四层：

### 5.1 配额层（谁能用多少）

- **平台级总配额**：每个用户 / 租户有并发实例数与总资源上限（如同时运行 ≤ N 个 agent、总内存 ≤ X GB）。
- **单实例规格（instance class）**：用户创建时选档，直接映射容器 `resources.requests/limits`：

  | 规格 | 配置 | 适用 |
  |---|---|---|
  | 轻量 | 0.5C / 1G | 客服问答、低频调用 |
  | 标准 | 2C / 4G | 带工具调用、中等负载 |
  | 性能 | 4C / 8G+（可选 GPU） | 推理重活、高并发 |

### 5.2 调度层（怎么跑，避免闲置浪费）

- **scale-to-zero（缩容到零）**：大部分 agent 空闲时缩容到零（释放容器），有对话请求再冷启动（数秒内拉起），仅对高活跃 / 付费 agent 常驻。
- 对应我们方案里的"启动"动作：启动 ≠ 常驻占用，而是"分配规格 + 拉起 / 唤醒"，容器实例随启停动态创建 / 释放。

### 5.3 回收层（不用了怎么办）

- **空闲自动休眠**：N 分钟无对话 → 自动缩容到零，释放资源，状态 / 配置保留。
- **主动停止**：控制台"停止"按钮手动释放。
- **配额超限拒绝**：超总配额时拒绝新建 / 启动，提示升级套餐。

### 5.4 计量与计费层（公平性）

- 按 **运行时长 × 规格** 计量（vCPU·小时、内存·小时），对接套餐 / 按量计费。
- 仪表盘展示每个 agent 的资源占用与费用（可扩展 MVP 的 metrics 卡片）。

### 5.5 对 status 模型的扩展

| status | 含义 | 是否占资源 / 计费 |
|---|---|---|
| `deploying` / `initializing` | 部署中、未就绪 | 否 |
| `running` | 已分配资源、可对话 | 是（计费中） |
| `stopped` / `scaled-to-zero` | 已释放 | 否 |

"启动"= 申请配额 → 调度拉起 → `running`；"停止 / 休眠"= 释放资源 → `stopped`。

## 六、高并发稳定性方案（万级用户同时调用）

目标：1 万用户同时调用时，系统不被冲垮。核心是"请求不无脑直冲后端 + 资源有上限 + 超载可降级"。以下五道防线从入口到实例逐层设防。

### 6.0 并发治理的责任归属（平台 vs Agent，基于独立子域）

采用独立子域后，需厘清"万级并发到底压在谁身上"。结论：**并发治理的主权在平台侧，单个 Agent 实例是被托管的隔离承载方，不直接面对全平台洪峰。**

- **总闸门在平台网关**：所有 `*.bairui.app`（含每个 `agent-{id}.bairui.app`）流量统一过平台入口网关（见 3.1 / 3.2）。万级用户的请求洪峰在到达任何 Agent 实例之前，就被平台的限流 / 多租户配额 / 队列削峰挡住和摊平。
- **独立子域让隔离更干净**：网关按 `Host: agent-{id}.bairui.app` 路由，天然知道流量属于哪个 Agent，配额 / 限流 / 计量都能精确落到单 Agent 维度。一个 Agent 实例异常，不会拖垮其他 Agent 或其他用户（按域隔离，见 3.1）。
- **五道防线的归属**：第 1、2、5 道（入口限流、队列、熔断降级）纯平台侧；第 3 道（弹性伸缩）平台编排；第 4 道（单实例硬限）平台设 limits、实例遵守。Agent 本体自身不实现全局并发治理，只保证对话循环在给定 limits 内不失控（见 6.0.1）。
- **一句话**：并发治理是平台的主权能力（入口统一、全局调度、熔断降级都在平台）；每个 Agent 子域作为被托管的隔离实例，享受平台给的弹性与硬限，自己不必也不应单独去扛洪峰。

### 6.0.1 单 Agent 实例需要 / 不需要考虑什么

基于"每用户每 Agent 独立实例 + 独立子域"的形态（第一、二节），需修正一个常见误解：**单个 Agent 子域是单一用户独占的，不会出现多用户同时调用它的情况。** 因此单 Agent 维度的并发治理基本不存在。

- **不需要考虑的（并发层面）**：万级用户同时调用的全局限流、队列削峰、跨租户调度——这些在平台网关层已处理，不会直冲到单实例；且由于每个 Agent 子域归属单一用户，单 Agent 背后**不会有多用户并发**（不同于"一个公开机器人被万人调用"）。单 Agent 的同时使用最多是该用户自己的多个标签页 / 多个会话，量级极小，谈不上并发治理。
- **平台仍兜底的"实例密度"**：万级用户 × 各自若干 Agent = 海量独立实例，压力落在平台编排层（管理 / 调度 / 路由海量子域实例），而非单个 Agent 扛并发。平台按 `agent_id` 给每个实例配副本 + `resources.limits`（第 3、4 道），防止单实例失控吃满节点。
- **必须自己守的"单点失控"**：若对话逻辑有 bug（死循环、无限工具调用、内存泄漏），会在自身 limits 内吃满单个副本；平台用超时熔断 + OOM 硬限兜住不扩散，本体需保证单次对话有超时、工具调用有上限、不无限递归。
- **仅当本体有共享状态时才需自管并发安全**：若 Agent 维护全局单例 / 共享连接池 / 全局缓存，需自己做成并发安全；按已定的"无状态 + 配置外置"（B1 / B2）设计，此层基本可规避。
- 结论：**全局并发归平台（入口统一 + 海量实例编排）；单 Agent 因单用户独占而基本无需考虑并发，只需保证自身不失控、按无状态设计。**

### 6.1 规模压力在平台编排层（非单 Agent 扛并发）

基于 6.0.1：单 Agent 因单用户独占、无多用户并发，不存在"被打爆"问题。但**单 Agent 运行时仍然占用资源**——每个容器实例按其规格档（见 5.1：轻量 0.5C/1G、标准 2C/4G、性能 4C/8G+GPU）稳定消耗 CPU / 内存，重负载还占 GPU。真正的规模压力来自**海量独立实例的资源总和与编排密度**——万级用户 × 各自若干 Agent = 海量容器实例的算力需要被调度、路由、计量、回收。粗略量级参考（按实例密度 × 单实例规格，而非会话并发）：

- 单实例资源占用：以标准档 2C/4G 估算，一个常驻 Agent 即占 2 vCPU + 4GB；即使用户只有一个标签页在对话，容器底座与模型上下文也按此规格保底。
- 集群总量级：若平均每用户持 5 个 Agent、峰值 1 万用户活跃 → 约 5 万常驻 / 唤醒中的容器实例，按标准档合计约 **10 万 vCPU + 20 万 GB 内存**，需平台编排层（网关 + 调度 + 节点池）统一管理；这些算力压力落在平台侧，而非单个 Agent 承受。
- 若模型推理走第三方 API，平台自身仅承担编排 / 路由 / 计量，压力集中在网关 + 调度 + 队列，可控；GPU 等重资源可单独池化、按需分配。
- 结论：单 Agent 的"资源占用"是**真实的、按规格档计费的**（见 5.4）；平台的规模挑战是**把海量实例的占用总和管住**，而非应对单实例的并发洪峰。

### 6.2 平台侧稳定性防线（治理实例密度）

并发治理主权在平台（6.0）。以下防线用于"海量实例编排不失控"，而非"单 Agent 抗洪峰"：

| 防线 | 手段 | 解决的问题 |
|---|---|---|
| 第 1 道：入口限流 + 多租户配额 | 网关层总 QPS 上限；每用户并发实例数 / 资源配额（令牌桶 / 漏桶平滑突发） | 单用户暴涨拖垮全局、实例数失控 |
| 第 2 道：异步化 + 队列削峰 | 启动 / 冷启动请求进消息队列（Kafka / Redis Stream），调度器按容量拉起容器，避免瞬时创建风暴击穿编排层 | 瞬时大量启动请求击穿后端，解耦请求与计算 |
| 第 3 道：节点池 + 弹性伸缩 | Swarm 集群多节点 + 按 CPU / 队列长度自动伸缩 service 副本或集群节点；预热镜像降冷启动；GPU 单独节点池化 | 实例太多打满集群、闲时浪费 |
| 第 4 道：单实例资源硬限 | 容器 `resources.limits` 锁死上限；OOM / 超时熔断 + 自动重试降级 | 单体实例失控吃满节点（兜底单点 bug，非抗并发） |
| 第 5 道：熔断 + 降级 + 背压 | 模型 API 侧并发控制 + 指数退避重试；异常率过高熔断；队列满向上游返回"繁忙" | 连环雪崩、内存堆积拖垮全站 |

### 6.3 与现有方案的衔接

- 第五节"配额 / 单实例规格 / scale-to-zero"对应第 1、3、4 道防线。
- 新增需补：**网关限流、队列削峰、自动伸缩、熔断降级**（第 2、3、5 道），构成完整稳定性体系。

### 6.4 落地节奏

- **MVP**：做"每用户配额 + 单实例 limits + 启动 / 停止 + 资源占用展示"（纯前端 mock 也可演示）。先不做队列与自动伸缩。
- **规模期**：上消息队列 + Docker Swarm 集群多节点调度与 service 自动伸缩 + 网关限流 + 熔断降级，全部为 Swarm 原生或标准云原生实践，工程量中等但必要性高。MVP 阶段即可直接用单/少节点 Swarm 集群（无需 K8s），本体打成镜像后由 Swarm 按 `agent_id` 起 service 即可。

## 七、前端 MVP 不阻塞后端建设

当前前端可在**无真实云**情况下完成产品闭环演示：

- 控制台纯前端 mock。
- "对话进云端"仅需 `embedUrl` 字段：启动后填入该 Agent 的稳定独立域名 `agent-{id}.bairui.app`，控制台"对话"按钮跳转 / 打开该域名即可使用本体 UI。
- 后端 runtime 就绪后，将 `embedUrl` 换成真实启动返回的域名，**前端结构无需改动**。

## 八、落地责任划分（平台侧 vs Agent 本体）

本形态下，平台是"让本体按用户独立跑起来"的运行时与路由层，Agent 本体是"被托管、被装载"的能力提供方。落地不要求本体重写对话能力，但本体需做最小适配以被平台实例化、注入配置、作为独立站点在专属子域提供服务。按"谁主导、谁交付"划分如下。

### 8.1 总体责任占比

| 责任域 | 主导方 | 占比 | 说明 |
|---|---|---|---|
| 部署 / 编排 / 多实例隔离 | 平台侧 | 100% | 核心主权，不依赖本体配合 |
| 对话路由 / `embedUrl` 分配 | 平台侧 | 100% | 网关、子域、鉴权 ticket 全在平台 |
| 控制台前端（管理面 + 壳） | 平台侧 | 100% | 创建 / 部署 / 启动 / 监控 / 配置 |
| 资源配额 / 调度 / 回收 / 计量 | 平台侧 | 100% | 见第五、六节 |
| 本体对话能力（UI / 循环 / 模型 / 记忆 / 工具） | Agent 本体 | 100% | 既有能力，平台不重写 |
| 本体可被平台托管的最小适配 | Agent 本体 | 主体 | 平台侧提供契约与接入规范，本体按规范改 |
| 集成呈现（独立域名直访） | 共担 | 平台定方案、本体放出口 | 本体只需可被独立部署为完整站点，在平台分配的稳定子域 `agent-{id}.bairui.app` 自行渲染 UI 供用户使用 |

> 结论：**平台侧主导 80%+ 的落地工作量与全部主权基础设施；Agent 本体只需做"能被实例化 + 能被配置 + 能被呈现"的最小适配**，且适配方式由平台侧定义并下发规范。

### 8.2 平台侧交付清单（主导）

| 序号 | 交付项 | 章节依据 | 是否自有 / 必做 |
|---|---|---|---|
| P1 | 实例化 / 编排服务：基于本体模板拉独立实例、注入配置、分配 `embedUrl` | 三、4.1 | 必须（核心） |
| P2 | 本体前端托管：平台域名下出独立子域 / 子路径 | 三、二 | 必须（地址自有） |
| P3 | 用户配置注入（API Key / 模型 / 渠道）与密钥隔离 | 三、一 | 必须 |
| P4 | 多租户隔离：配置 / 会话 / 运行时互相隔离 | 三、二 | 必须 |
| P5 | 启动 / 停止 / 休眠 动作与 `status` 流转 | 4.3、5.5 | 必须 |
| P6 | 控制台前端改造：移除 mock 对话，"对话"按钮跳转 / 打开该 Agent 稳定独立域名 `agent-{id}.bairui.app` | 四、4.3 | 必须 |
| P7 | 鉴权 ticket：短期签名，用户访问独立域名时经平台登录态校验（不再用 URL 注入 ticket） | 3.1 | 必须 |
| P8 | 资源配额 / 单实例规格 / scale-to-zero / 计量计费 | 五 | 必须（MVP 先配额 + limits） |
| P9 | 高并发五道防线：网关限流、队列削峰、弹性伸缩、单实例 limits、熔断降级 | 六 | 规模期必做 |
| P10 | 接入规范与契约：下发实例化 / 配置注入 / 子域分配契约，约束本体可被独立部署为完整站点 | 三（本体改造） | 必须（约束本体） |

### 8.3 Agent 本体交付清单（最小适配）

| 序号 | 适配项 | 章节依据 | 要求 |
|---|---|---|---|
| B1 | 配置外部化：API Key / 模型 / 渠道从环境变量 / 配置中心读取，不写死 | 三（本体改造） | 必须 |
| B2 | 无状态化 / 支持多租户参数：按 `agent_id` 区分配置与数据 | 三（本体改造） | 必须 |
| B3 | 可被独立部署为完整站点：作为自包含 Web 应用在平台分配的稳定子域 `agent-{id}.bairui.app` 自行渲染对话 UI，无需依赖控制台壳内挂载 | 二、4.2 | 必须 |

> 鉴权说明：方案 A（iframe + ticket 注入 URL）已弃用，方案 B（壳内注册表 / 适配器内嵌）一并移除。对话不在控制台壳内进行，用户直接访问独立域名使用 Agent 本体 UI，平台 ticket / 登录态在独立子域侧校验即可，本体无需实现"壳内挂载点"或"跨域事件映射"。

### 8.4 责任边界红线

- **平台侧不碰**：重写对话逻辑、替换本体模型运行时、修改本体核心 Agent 循环。
- **本体侧不碰**：实例编排、子域 / 路由、配额 / 计费、跨用户隔离、平台壳 UI。
- **共建约定**：`embedUrl` 字段（= 稳定独立域名）、实例化 / 配置注入契约、ticket 格式由平台侧定义，本体按规范实现，避免两边各写一套。
