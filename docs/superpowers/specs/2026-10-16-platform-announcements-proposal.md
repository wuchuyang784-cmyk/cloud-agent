# 平台公告功能开发方案

日期：2026-10-16 开始，2026-10-17 更新。用户已确认推荐方案并先后授权 A、B、C、D 批；A 底座、B 管理端、C 业务端接收与 D 定时发布/故障恢复已开发并隔离验收，未提交或部署。E 目标环境部署仍未交付。各批范围与验收见 `docs/52-platform-announcements-a.md`、`docs/53-platform-announcements-b.md`、`docs/54-platform-announcements-c.md`、`docs/55-platform-announcements-d.md`。

## 1. 能力与范围

平台管理员在现有管理端创建、编辑、预览公告，选择立即发布或定时发布；发布后业务端用户在原通知中心查看公告、未读数和详情。关键操作留存数据库审计，发布时间与可见性在双 API、多发布器和进程重启下保持一致。

用户明确的核心要求：管理端编辑发布、可选择发布时间、面向全部业务账户、审计发布操作。下文有效期、新注册用户可见性、已发布内容不可直接改写等最初为建议默认规则，已随用户确认方案开始 A 批而确定。

第一期不包含短信、邮件、企业微信、强制阅读弹窗、附件上传、富文本 HTML、多级审批、分组织或分人群投放。它是平台广播，不是跨用户业务数据共享。

## 2. 当前仓库可复用部分

- `apps/console-mvp/src/App.tsx` 已有通知铃铛、红点、通知弹层和已读操作；弹层只显示前 12 条，尚无公告详情/历史分页。
- `packages/db/migrations/028_agent_user_features.sql` 已有按组织与用户隔离的 `user_notifications`，PostgreSQL 查询最多返回 50 条，通知类型约束不包含公告。
- `/api/user/notifications`、`/read-all` 和单条 PATCH 已存在；两种 Store 都已有个人通知实现。
- 管理端已有 Better Auth、平台角色、治理状态和审计查询模式，但没有公告模块、公告写权限或公告发布器。现有 `platform_admin_audit.action` 只允许既有三类事件，不宜直接塞入任意公告 action。
- 当前客户端通知加载失败会降为“空列表/0 未读”；单条已读直接减一、全部已读直接清零。公告接入需要同时改为服务端权威计数与会话/请求代次隔离，防止重复扣数、错误清空和账号切换后的迟到响应。
- 暂停账户在 API 层是只读，封禁账户拒绝会话。公告不能绕过这些现有治理边界。

## 3. 两种落地方式

推荐“共享公告 + 稀疏个人已读记录”：每条公告只保存一份，读取时合并到当前用户通知列表；只在用户标记已读时写个人回执。发布不需要枚举、复制全部账户，离线用户和新用户按可见规则读取。

备选“逐账户分发通知”：异步给每个账户插入个人通知，易于形成固定收件人快照，但需要批次、断点、去重和注册补发；存储与发布任务量随人数增长。只有产品明确要求冻结收件人名单、逐人发送结果时才采用。

第一期不建设通用消息总线；可保留以后接邮件/短信的扩展点，不提前引入 Redis/Kafka 或 WebSocket。

## 4. 建议业务规则

### 4.1 内容与可见范围

- 标题 1–120 字，正文 1–20000 字；第一期纯文本与换行，禁止原始 HTML、脚本和外部嵌入；可选“普通/重要”级别和置顶。
- 公告只能面向全平台业务账户，不附带其他用户、组织或 Agent 的私有信息。
- 新注册账户可以查看当前仍有效的公告；离线账户登录后能补看。有效期默认 30 天，可改为长期有效。
- 公告未到发布时间、仍为草稿、已撤回时，不得出现在业务端列表、未读统计或详情接口。
- 过期公告不再提醒、不给新用户制造未读积压；公告历史可保留已发布内容并标注已结束。撤回公告从后续用户查询移除，不能保证抹除用户已经看过的内容。
- suspended 账户仍能只读查看公告，但标记已读遵守现有写入拒绝；banned 账户不能登录。解除治理不恢复旧会话。

### 4.2 状态与修改

主状态：`draft / scheduled / published / withdrawn / expired`。

- 草稿可编辑、预览；立即发布进入 published，定时发布进入 scheduled。第一期不增加归档状态。
- 待发布可取消定时退回草稿；更改内容或时间必须提交新版本并重新确认。
- 已发布正文保持不可变；纠错采用撤回后复制为新公告发布，保留原公告和原发布审计。撤回必须填写原因。
- 已撤回或过期公告不重新激活；再次发布复制成新公告，避免旧已读状态被无意复用。
- 过期可见性由数据库当前时间判定，不依赖后台进程及时清理状态；发布器后续收敛 expired 并记录系统事件。

### 4.3 时间

- 编辑界面明确显示时区，默认 Asia/Shanghai；API 接收带时区的 ISO 时间，数据库存 `timestamptz`，以数据库时钟决定是否到期。
- 定时发布时间必须在未来；已经过去的时间不能静默改成立即发布。客户端时钟只负责展示，不参与最终准入。
- 记录计划时间和实际生效时间，界面区分“待发布”“发布延迟”“已发布”，不把保存定时任务称为已发布成功。
- 正常健康环境目标：发布器约每 5 秒检查，前台页面约每 30 秒刷新，在线感知目标约 40 秒内；这是目标，不是故障场景下的时限保证。

## 5. 页面与使用体验

### 管理端

在现有五项导航外新增“公告管理”，不替换账号、Agent、监控和告警页面。公告与 Prometheus 告警分开。

列表包含标题、状态、级别、计划/实际发布时间、有效期、最近操作者及版本，支持状态筛选、搜索和游标分页。行操作按状态显示编辑、预览、发布、取消定时、撤回、查看审计、复制为新公告。

编辑页包含标题、正文、级别、置顶、发布时间和有效期。发布前展示内容摘要、覆盖范围、时区与时间；前端提示与数据库版本校验共同防止过期页面覆盖他人修改。

每条公告详情提供审计时间线。第一期不用新增通用审计中心，也不把审计功能塞进业务端。

### 业务端

复用原通知铃铛，新增公告类型和详情。弹层展示最近通知并提供“查看全部”，完整通知/公告列表支持分页和已读/未读筛选，旧计费/系统通知继续保留。

点击公告成功加载详情后再标记已读；单条与全部已读均幂等，已读数来自服务端。全部已读针对服务端同一操作的可见快照，之后发布的新公告保持未读；不能只是把红点强行置零。

登录、打开通知、窗口重新获得焦点或恢复可见时刷新；页面可见时每约 30 秒轮询，有界超时、单轮去重、隐藏时暂停。刷新通知不重载整个控制台或触碰 Agent 能力开关。

失败时显示“通知暂不可用/上次更新”，不伪装成没有公告；退出或账号切换立即清空个人状态，迟到响应不能恢复旧账户内容。

“对全员可见”“浏览器获取到”“用户标记已读”是不同事实。第一期不提供伪造的全员送达率；已读统计只能表示用户执行了已读动作，不证明理解了内容。

## 6. 数据与权限

建议新增三个表；迁移暂定 `041_platform_announcements.sql`，实施时以仓库当时实际编号为准。

1. `platform_announcements`：公告 ID、标题/正文/级别/置顶、主状态、版本、创建/编辑/定时责任人、计划与实际发布时间、有效期、撤回信息，以及重试时间、次数和安全错误码等调度字段。
2. `platform_announcement_receipts`：公告 ID、个人空间组织 ID、用户 ID、已读时间；组合唯一约束，写入主体来自 Principal，用户不能读写别人回执。
3. `platform_announcement_audit`：公告 ID、操作者、执行者类型、action、请求 UUID、前后版本、字段摘要、内容哈希、计划/实际时间、原因、数据库时间及幂等结果。不得由浏览器提供 actor。

保存和发布的已提交操作使用请求 UUID + 参数摘要去重；同键不同参数返回 409。版本不匹配返回 409，不静默覆盖。公告保留已发布内容，审计不记录 Cookie、密码、Key；HTTP 错误与指标不得包含正文或用户标识。

三类平台角色建议：viewer/operator 可看公告列表和审计；只有 active 的 platform_admin 能编辑、发布、取消或撤回。新增明确的 announcements:read/manage 与 announcement-audit:read 权限，不以个人空间 org_admin 替代平台角色。

数据库沿用受限应用角色与固定授权函数：应用账号不能直接跨用户写公告/审计或访问他人回执；公告、审计和回执配置 RLS/最小 EXECUTE 授权。全平台共享仅限显式发布的公告内容，不放宽原 user_notifications 的个人 RLS。

DB 函数接收受信任 API 传入的 Principal；它不是数据库应用凭据泄漏后的独立身份认证系统。发布器使用独立受限数据库身份，只能领取/完成固定公告发布操作，不能创建任意正文、操作用户/角色或访问 Docker。

## 7. 审计闭环

至少记录 created、draft_updated、schedule_set、schedule_cancelled、published、withdrawn、expired、publish_blocked 等明确事件。

人工立即发布与定时发布均要求“状态变更 + 实际发布审计”在同一事务中提交；写审计失败则发布回滚。设置定时的审计不能替代实际发布审计。

定时发布记录原定时责任管理员、当时治理版本、实际系统执行者及实际时间。责任管理员暂停、封禁、撤权或治理版本变化后，不静默按旧授权发布；任务进入需确认的调度阻塞状态，由有效管理员重新确认。原管理员解除限制不自动恢复旧任务。

通过版本/治理围栏、数据库角色校验和统一锁序，使并发取消、撤回、账号治理和发布只有一个确定结果。禁止发布成功后再异步补一条容易丢失的审计。

## 8. 定时发布器

新增专用 `announcements:publisher` 进程，不复用当前关闭的旧 Agent Worker，不接入真实 Agent/编排器或模型调用。

- 约 5 秒一个有界周期，最多处理 50 条；数据库索引覆盖待处理时间，单次事务/查询有超时。
- 用行锁/SKIP LOCKED 与条件更新领取到期记录，按公告版本幂等提交；多副本和重试只允许一次有效发布和一条对应发布审计。
- 不跨网络持有数据库事务。发布不需要逐账户 fan-out，也不在登录/GET 请求中偷偷触发发布。
- 服务重启后从 PostgreSQL 恢复；错过时间但仍有效的公告补发，记录实际延迟。已过有效期则跳过发布并记录过期，不补发过时公告。
- 数据库暂不可用等瞬时错误退避重试；版本或权限冲突不自动绕过。单条失败不能饿死其他任务。
- 保存失败安全码，不给用户虚报成功；提供发布器心跳、到期待处理数、最大延迟、失败次数等低基数指标，接入既有监控。
- 部署作为独立受限服务随平台发布，保留 API 双副本兼容；不因增加公告而开放旧执行入口。

## 9. 拟定接口

管理端：

- `GET/POST /api/admin/announcements`：列表/创建草稿。
- `GET/PATCH /api/admin/announcements/:id`：详情/编辑草稿。
- `POST /api/admin/announcements/:id/publish`：立即发布或设置定时，携带 mode、scheduledAt、expectedVersion、requestId。
- `POST /api/admin/announcements/:id/cancel-schedule`：取消定时退回草稿。
- `POST /api/admin/announcements/:id/withdraw`：撤回，携带版本、请求 UUID 和原因。
- `GET /api/admin/announcements/:id/audit`：有界审计分页。

业务端：

- 兼容扩展 `GET /api/user/notifications`：合并本人旧通知与有效公告，增加 source、referenceId、摘要、分页和权威未读数；保持旧字段可用。
- `GET /api/user/announcements`、`GET /api/user/announcements/:id`：公告列表/详情，过期历史明确区分，草稿与撤回返回 404。
- `POST /api/user/announcements/:id/read`：只记录本人已读，重复调用成功且不重复计数。
- 原通知单条 PATCH 保持个人通知语义；`/notifications/read-all` 兼容覆盖当前可见公告，不接受客户端传 userId/orgId。

所有写接口同源校验、认证、权限检查、严格字段/长度限制与限流；查询游标与 limit 有界。公告列表、详情、个人未读和审计均 no-store，监控指标只记录固定路由标签。

## 10. 代码组织建议

- 后端新增 `src/announcements/` 领域目录，分离验证、生命周期、Store、用户查询与发布器；管理路由接入现有 admin 授权，不继续把全部业务追加到 app.mjs。
- Memory/PostgreSQL 双实现共享契约，测试时注入时钟；Memory 不替代真实受限 PostgreSQL 并发/RLS 验收。
- 管理端新增公告列表/编辑/审计组件与独立会话状态模块；沿用现有紧凑控制台风格。
- 客户端提取独立通知状态模块与公告详情组件，修复计数、分页、失败状态及请求围栏；保留原业务导航。
- 新增发布器配置、部署/停止/状态脚本与测试入口；dev/platform 启动变更需显式配置，不隐式启动 Agent Worker。

## 11. 开发顺序与验收

1. **A：数据库与权限底座。** 迁移、Store 双实现、草稿/状态/幂等/审计；临时 PostgreSQL 验证最小权限和 RLS。
2. **B：管理端与立即发布。** 编辑/预览/确认、发布/撤回、列表与审计；两名管理员并发版本冲突验收。
3. **C：业务端接收。** 复用铃铛、详情/分页、个人已读、权威计数、离线/新账号规则与会话隔离。
4. **D：定时与故障恢复。** 专用发布器、多副本抢占、重启补发、取消竞态、过期、权限撤销和重试；接监控。
5. **E：部署验收。** 完整回归、双 API 与真实 Better Auth/受限库浏览器验证；备份后对目标环境追加迁移与最小授权，发布 API/页面/发布器并核对历史通知未变。

每批先写失败测试再实现。测试入口拟为 test:announcements、test:announcements:db、test:announcements:web 与 test:announcements:publisher；名称为开发目标，当前还不存在。

关键验收包含：普通账号/个人组织管理员越权拒绝，草稿/未到期不可读，跨账户回执拒绝，重复发布和重复已读幂等，审计失败回滚，双 API/双发布器一次生效，取消/治理与到期发布竞态，离线与新注册补看，撤回与过期不计未读，全部已读后新公告仍未读，跨账号/乱序响应清理，轮询故障不显示假零，发布器停启恢复，旧系统/计费通知保持可用。

容量在一次性测试库构造万级账户与千级公告，记录发布事务耗时、通知列表查询计划、未读查询和轮询负载，确认发布不随账户数线性写入。不以本机小样本测试宣称生产容量保证。
