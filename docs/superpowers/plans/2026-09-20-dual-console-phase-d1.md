# D1 账号治理实施计划

目标：在现有双端平台上交付可审计的账号暂停、封禁、解除，不接真实 Agent、模型或服务器部署。

- [x] 后端测试先行：角色、来源、本人保护、版本、幂等和读写隔离。
- [x] 036 迁移：独立治理状态及审计表、最小权限函数、会话并发封禁保护。
- [x] 后端接入：Better Auth 会话钩子、每请求账号检查、管理写接口。
- [x] 双端界面：管理端确认操作与审计查询，客户端只读状态和错误提示。
- [x] 独立 PostgreSQL 双副本测试、前后端回归、构建与浏览器验收。
- [x] 中文技术路径、迁移授权和验收边界说明。

约束：只使用 Conda cloud；保留已有 C 批改动；不读取或修改业务库、真实账号、预发和服务器。默认不允许数据库缺表或权限故障时放行。只有 active 的 platform_admin 可以写治理状态，viewer/operator 只读；暂停账号可登录和读取本人数据，但不可使用管理端。业务请求按服务端状态准入，已准入的在途操作不承诺撤销，真实 Runtime 强停留给 D2。

数据设计：active / suspended / banned；从未治理的账号版本为 0；变更要求 expectedVersion、UUID requestId、原因。同一事务校验角色、保护本人及最后管理员、更新状态、追加审计、封禁时删除全部 Better Auth 会话。治理请求串行短事务保证管理员互封安全；会话创建与治理通过同一身份锁互斥，防止并发登录留下有效会话。解除不恢复旧会话或启动 Agent。

前端设计：沿用现有紧凑管理表格，账号状态单独列；操作弹窗必须输入原因；失败不显示成功；超时重试沿用相同请求号，过期页面先刷新状态。客户端展示暂停提示，服务端统一阻止业务写入。切换和退出清空治理表单、审计及旧请求结果。

验收不能将单元测试或独立数据库通过写成业务库、生产部署或真实 Agent 治理完成。
