# 第二阶段：Swarm 多进程验收

日期：2026-09-17。本批承接 34 号文档的模拟调度内核，不接入真实 Agent。

后续补充：可信代理和双 API 共享认证限流已接入同一验收脚本，最新实现与报告见 [36-platform-mode-and-auth-proxy.md](36-platform-mode-and-auth-proxy.md)。下方首次实测记录保留供追溯。

## 目的与边界

用真实独立进程验证注册登录、会话跨副本、任务归属、调度、Worker 中断恢复。复用开源 Better Auth 作为认证提供方，复用 Caddy 和 Docker Swarm，不再实现另一套认证或容器编排器。

这是可重复执行的本机验收环境，不是常驻业务部署。脚本不读取根目录 .env，不连接 bairui，不修改原账号、原服务或原 platform-stack.yml。每次临时数据库中的账号和任务均随验收环境清理。

## 一条命令执行

前提：本机 Docker Desktop 已运行，当前 Docker context 指向本机单节点 Swarm manager，Node.js 与后端依赖已安装。

在 PowerShell 执行：

~~~powershell
Set-Location E:\cloud-agent
npm run test:scheduler:swarm
~~~

不需要手动导入 033，不需要提供邮箱、密码或密钥。脚本自动创建测试账号，不发送邮件。
首次需要构建镜像，之后会复用构建缓存。账号准备阶段可能触发 Better Auth 的注册/登录限流，脚本按 Retry-After 有限等待，不关闭安全限制。任务接口的错误不会自动重试来掩盖失败。

成功时末尾显示：

~~~text
本次验收服务、容器、网络、凭据已清理；业务环境未修改。
验收报告：E:\cloud-agent\output\scheduler-swarm\bairui-swarm-check-<随机编号>.json
Swarm 验收通过：10 用户 / 50 基线任务 / 10 故障恢复任务。
~~~

脚本返回非零退出码或报告 success=false 即为未通过，不能仅根据某一项“通过”判断整体成功。

## 部署拓扑

~~~text
本机测试客户端
  -> 127.0.0.1:随机端口 / Caddy
  -> 独立 overlay 网络 / API Swarm service（2 副本）
  -> 独立 PostgreSQL
  <- Worker Swarm service（2 副本）
~~~

- API 与 Worker 是真实 Swarm 服务，每份副本为独立容器/Node 进程。
- Caddy 与数据库为加入同一 overlay 的独立临时容器，端口只绑定本机回环地址；它们不是 Swarm 高可用服务。
- Caddy 仅放行 healthz、认证和模拟任务路径。旧 Agent 与充值等路径不经此验收入口暴露；日常业务入口现有独立平台能力开关，见 36 号文档。
- Caddy 动态解析 tasks.<API服务名> 并轮询直连 task，避免本次 VIP 路径改变 TCP 来源；只信任本次 Caddy 的确切 overlay IP。关闭上游 HTTP 连接复用，以便本机小流量实际覆盖双 API；通过验收专用响应头检查实例和来源。
- 认证密钥、数据库连接串通过 Swarm Secret 提供。API 与 Worker 以 UID 1000 运行，不挂载 docker.sock。
- 应用使用独立非超级用户、无 BYPASSRLS 的 PostgreSQL 角色。只有本机验收脚本持有临时管理员凭据，用于迁移和采样。
- Dockerfile 专用忽略文件仅允许后端依赖清单和源码进入构建上下文，不包含业务 .env。

## 资源预算

| 组件 | 数量 | 单份 CPU 上限 | 单份内存上限 | Swarm 预留 |
| --- | ---: | ---: | ---: | --- |
| API | 2 | 0.5 核 | 384 MiB | 0.1 核、64 MiB |
| Worker | 2 | 0.5 核 | 256 MiB | 0.1 核、64 MiB |
| PostgreSQL | 1 | 1 核 | 512 MiB | 不适用，临时独立容器 |
| Caddy | 1 | 0.25 核 | 128 MiB | 不适用，临时独立容器 |

API 连接池每份最多 5，Worker 每份最多 3，验收管理员池最多 2。以上是进程容器预算，不是每个 Agent 的 CPU/内存预留。模拟任务仍为等待型任务，不能据此推算真实模型吞吐。

## 验收内容

1. 在临时库顺序执行迁移，并创建受限应用角色。
2. 启动两份 API 与两份 Worker。
3. 10 个用户经 Caddy 调用 Better Auth 注册、退出、重新登录，确认数据库记录和个人空间独立。
4. 同一登录会话访问两份 API，保持同一个平台用户身份；退出后的会话不可继续访问。
5. 10 人每人提交 5 个任务，共 50 个，时长 2 至 5 秒。确认两份 Worker 都实际领取执行。
6. 同幂等键不重复创建，其他用户查询和取消任务均返回 404，各用户只能列出自己的任务。
7. 每约 200 毫秒采样任务表，检查全局运行数不超过 10、单用户及单 Worker 不超过 5。
8. 另提交 10 个 5 秒任务，对当前正在执行这些任务的本次 Worker 容器发送 SIGKILL。
9. 确认至少一个受影响任务被重新领取并成功，执行尝试不超过 3，Swarm 恢复双 Worker 副本。
10. 保存脱敏报告，清理本次服务、容器、网络、Secret、Config 和镜像标签。保留构建缓存和验收报告。

不会对已有 bairui-postgres 或其他服务发送终止命令。不要关闭 Docker 或强制结束验收脚本进程，否则 finally 清理无法保证执行；普通 Ctrl+C 会在检查点转入清理。清理失败时会列出本次剩余资源名，不使用全局 prune。

## 如何读报告

- baseline：50 任务波次总耗时、平均完成速率，以及实际参与的 API/Worker 数量。
- recovery：故障信号、故障波次任务数、观察到的重试完成数、故障恢复耗时、恢复后的副本数。
- concurrency：采样次数与观察到的全局/用户/Worker 并发峰值。采样不是连续事件审计，完整状态机约束仍依靠调度单元与数据库测试。
- http：测试请求响应头耗时的 P95 和最大值，包含账号准备请求，不是纯调度接口压测指标。
- resources：基线执行期间、故障恢复后的 docker stats 快照，不是整个过程的 CPU/内存峰值。
- authRateLimitWaits：账号准备遵守认证限流的等待次数。
- authRateLimit：并发错误登录的放行/拒绝数、覆盖 API 副本数、另一真实客户端是否保持独立。
- proxy：本次临时 Caddy 受信 IP、API 实际 TCP 对端和识别出的客户端 IP；不能直接复制到业务配置。
- cleanup：本次资源清理是否完成。

报告不保存密码、数据库 URL、密钥或 Cookie。失败报告只保存状态码、错误类别及检查名称。

## 本机实测记录

2026-09-17，报告编号 bairui-swarm-check-f1485af173：

- 实际 API 2 副本、Worker 2 副本，10 个用户的 50 个基线任务全部完成，波次耗时约 31.0 秒。
- 全程 270 次采样，观察到的运行峰值为全局 10、单用户 5、单 Worker 5，未发现超限。
- 对正在运行的 Worker 发送 SIGKILL，故障波次 10 个任务全部完成，其中观察到 5 个任务重试；从发送终止指令到任务完成及双副本恢复约 21.4 秒。
- 账号准备遵守注册限流，共等待 3 次；未关闭认证限流。
- 容器资源快照及脱敏报告保存在 output/scheduler-swarm；本次临时资源已清理。

这是一轮实测记录，不是性能 SLA，也不表示常驻业务环境已切换。

## 尚未覆盖

- 多主机、节点故障、数据库高可用、网络分区或连接池耗尽。
- 常驻环境部署与回滚、浏览器控制台的模拟任务页面。
- 其他入口拓扑的可信代理配置与公网直连隔离。本机 Caddy 的精确 IP、伪造头防护、双 API 共享限流和独立真实客户端已经验收，但不能据此信任整个 overlay 或任意代理来源。
- 实际 Agent 的 CPU/内存配额、资源放置、Provider 限流和业务副作用幂等。
- 持续监控、任务事件审计、长时间压测与容量结论。

本机闭环通过后再按上述边界推进，不能把本报告当作生产高并发或跨主机高可用认证。
